用历史 Browser Executor 方案练习深 Module

目标：你能判断一次重构是在提高 Depth，还是只把一个大文件切成更多小文件。

历史案例：本课分析的是未实施的 fallback deep-module 方案， 不是当前实现计划。当前 Development 路径是 packages/browser_runtime； 长期 Formal 决策由 ADR 0004定义。

1. 先看当时的问题

历史 runtime 的困难不只是 browser_runtime.py 有 4,847 行，而是一次 cleanup 规则变化会迫使 runtime、supervisor、scenario、protocol、reviewer 和测试一起修改。复杂度穿过了多个 caller 能看见的 Interface，Locality 很低。

伪重构：把 _PinnedExecutable 拆成四个 class，但仍让 caller 按顺序调用 mount()、launch()、connect()、cleanup()。文件变小，Interface 反而更大。

2. fallback 方案选定的两个 Seam

公开 Seam
render_residual_preview(request) -> RenderedPreview

私有执行 Seam
BrowserExecutor.execute(sealed_job) -> BrowserExecution

外部 caller 不学习 browser。私有 executor 一次性拥有 authority、Source-Hidden、launch、CDP、render、cleanup 和 evidence。Darwin 与 Linux 是两个真实 Adapter，所以这个 Seam 不是为测试虚构的。

Depth：caller 学一个动作，却得到完整八视图渲染和所有安全生命周期保证。

3. 内部仍可拆，但不扩大 Interface

  • FrozenBrowserTree：manifest、copy、freeze。
  • BrowserExecutionTree：只读 execution tree 与 Source-Hidden。
  • OwnedBrowserProcess：process group、readiness、listener、CDP。
  • CleanupLedger：首个 predicate 与 retained proof 仲裁。

它们是 executor Implementation 内的 Module。caller 不组合它们，也不承担调用顺序。

4. 为什么 Source-Hidden 不等于只读

如果 Chromium 能通过 /proc/<supervisor>/root 解析 source，即使打开写模式失败，它仍知道 source 的存在和内容。规格要求的是看不见，因此新拓扑让 source-owning materializer 留在 renderer 的 PID namespace 之外，并给 renderer 一个私有 /proc。

5. 三个检索练习

Q1. caller 新增 runtime_mode 和 cdp_endpoint，Module 变深了吗？

没有，内部知识泄漏到了 Interface。

Q2. 为什么 fallback 方案没有定义可插拔的 direct-CDP Adapter registry？

当时只有一个真实控制 Adapter，Seam 仍是假设。

Q3. 哪个验收事实能证明 Source-Hidden？

所有 renderer-visible source aliases 都无法解析。

6. 你现在可以怎样评审方案

  1. 圈出 caller 必须知道的全部事实；它们共同构成 Interface。
  2. 做删除测试：删除 Module 后，复杂度会消失还是散回 caller？
  3. 检查每个 Seam 是否至少有两个真实 Adapter。
  4. 确认新测试穿过 Interface，而不是继续 patch 私有 syscall。
