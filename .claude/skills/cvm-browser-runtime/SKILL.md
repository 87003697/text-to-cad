# CVM Browser Runtime

Use this workflow for the single Browser Runtime image consumed by pilot jobs.
Its public Interface is exactly `prepare → provision → probe`.
`status <handle>` is a read-only diagnostic for retrieving immutable remote
receipts after a failed operation; it never retries or changes lifecycle state.

## Workflow

1. Start from a reviewed clean checkout. Build from an exact Git archive, not
   the workspace directory, so ignored outputs and caches never enter the
   multi-gigabyte Docker context. Pass the same 40-hex revision as
   `SOURCE_REVISION`; the Dockerfile places its provenance label after the
   expensive dependency layers so a revision-only rebuild reuses them.

   ```bash
   git archive --format=tar <40-hex-reviewed-sha> |
     docker build --platform linux/amd64 \
       --build-arg SOURCE_REVISION=<same-40-hex-reviewed-sha> \
       --tag text-to-cad-browser-runtime:build-<short-sha> \
       --file packages/browser_runtime/image/Dockerfile -
   ```
2. Prepare locally:

   ```bash
   scripts/pilot/cvm-browser-runtime.sh prepare \
     --source-revision <40-hex-image-source-sha> \
     --runtime-image sha256:<64-hex-image-id>
   ```

   Completion criterion: the receipt is `status:"prepared"` and binds the
   exact image ID, revision, archive SHA-256, workflow revision, and workflow
   file hashes.
3. With explicit CVM provision authorization, run:

   ```bash
   scripts/pilot/cvm-browser-runtime.sh provision <cvmbr-handle>
   ```

   Completion criterion: the receipt is `status:"provisioned"`, the transferred
   archive and its generated transport tag are absent, and one exact retained
   runtime image ID is recorded. Docker engines may assign different local
   IDs to the same saved artifact. Provision therefore re-inspects the loaded
   image, requires the same role, platform, and source-revision label, then
   atomically rewrites only the CVM checkout's image-lock ID to that observed
   exact ID. This is host-local identity binding, not tag selection or fallback.
4. With explicit one-shot probe authorization, run:

   ```bash
   scripts/pilot/cvm-browser-runtime.sh probe <same-cvmbr-handle>
   ```

   Completion criterion: the receipt is `status:"succeeded"`, a fixed triangle
   produced a PNG through `BrowserRuntimeJob.preflight`, and the probe container
   and network are absent.

## Invariants

- One handle owns one immutable runtime image and one terminal provision/probe.
- The source image is exact `linux/amd64`, has an exact SHA-256 ID, and carries
  the exact reviewed source revision label.
- Provision requires `3 GiB + archive bytes` before transfer and retains a
  3 GiB reserve after load.
- The wrapper and Module deployed by `cad:cvm-push` must match the locally
  prepared hashes.
- The remote archive reference is generated by the Module and must be absent
  before load.
- `cad:cvm-push` installs the reviewed source lock; successful provision is the
  only operation allowed to rebind its CVM copy to the attested host-local exact
  ID. Run provision after every push that replaces that lock.
- The probe uses the same `BrowserRuntimeJob` and fixed residual preflight as
  production pilots.
- A failed handle is terminal. Create a new reviewed image and handle for the
  next attempt.

## Authorization

`prepare` is local. `provision` and `probe` are separate CVM writes and each
requires explicit authorization. Neither operation authorizes a paid pilot,
output upload, or image deletion.

## Validation

The local fake-boundary suite is:

```bash
python3 -m unittest tests.python.global.test_cvm_browser_runtime
```

The suite performs no CVM access. The public `provision` and `probe` commands
are the only remote execution paths.
